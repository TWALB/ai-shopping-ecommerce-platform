# 上线前安全审计报告 —— 基于大模型导购的数码电商平台

## Meta

- 审计人：gstack-security-officer (CSO)
- 范围：`code/backend` 全部 Java 源码与配置、`code/frontend/src`、建表 SQL、Git 提交历史（排除 node_modules/dist/target）
- 方法：OWASP Top 10 (2021) 逐项排查 + STRIDE 威胁建模 + 代码级主动验证（静态溯源确认利用路径）
- 审计日期：见 Git 最新提交 4aed888 之后的当前工作区

## 执行摘要

系统整体安全架构**高于同类毕设平均水平**：密码 BCrypt 哈希、JWT + Redis 双校验单端登录、角色实时校验、SQL 全参数化（未发现任何 `${}` 注入点）、订单/售后/购物车/地址/会话等核心实体均有归属校验、商家跨店校验完备、密码字段 `@JsonIgnore`、全局异常不泄露堆栈。

但发现 **1 个 🔴 级业务逻辑漏洞：下单数量未校验，可构造负数量/零数量订单实现金额篡改与"零元购"**；另有售后累计超退、验证码无试错次数限制（可爆破重置任意账号密码）、改密/找回密码口令走 URL 查询参数、验证码明文落日志、硬编码密钥等 🟠 级问题。

**结论口径（已与代码评审/QA 三方对齐，按"暴露模型"分级）**：
- **本机 localhost 演示验收**：No-Go。无条件阻塞 6 项 = 演示路径 4 项（含 F-001）+ 正确性 2 项（含 F-002 合并项）。
- **非 localhost 部署（局域网/云服务器）**：追加 3 项安全条件阻塞（F-003 验证码爆破、F-005 口令入 URL、F-006 验证码落日志须开关化），其中 F-003 优先级升至最高（直接账号接管）。
- 修复无条件 6 项 + 条件项按部署场景裁剪后，可复审为 Go。

## 发现清单（严重度分级）

### 🔴 阻塞（Blocker）

#### [F-001] 下单数量未校验：负数量金额篡改 / 零元购
- **Category**: A04 不安全设计 / 支付完整性
- **Confidence**: 10/10（代码路径完整确认）
- **位置**:
  - `controller/OrderController.java:30` — `create(@RequestBody CreateOrderRequest request)` **无 `@Valid`**
  - `dto/CreateOrderRequest.java:24-28` — `OrderItemLine.quantity` **无任何校验注解**
  - `service/impl/OrderServiceImpl.java:99-127` — `createOneOrder()` 直接使用 quantity
  - 同源问题：`CartServiceImpl.java:38-75` 加购/改数量仅校验上限 `> stock`，不校验下限
- **威胁描述**: `quantity` 可为负数或 0。扣库存语句为 `stock = stock - {quantity}` 且条件为 `stock >= {quantity}`：
  - `quantity = -5`：条件恒真，库存反增 5，订单金额 `price × (-5)` = **负金额**，支付流水记录负数；
  - `quantity = 0`：条件恒真，生成 **0 元订单**，模拟支付直接成功 → 商品"零元购"，销量照常累加；
  - 购物车路径同样可注入负数量（`updateQuantity` 无下限），结算时进入同一逻辑。
- **利用场景**: 注册普通账号 → `POST /api/order` 提交 `{"addressId":X,"fromCart":false,"itemList":[{"skuId":1,"quantity":0}]}` → `POST /api/payment?orderId=...` 支付成功 → 商家后台出现待发货的 0 元订单。
- **补充分支（QA 交叉确认）**: `quantity=null`（漏传字段）走 `ge(stock, null)` 恒假 → 返回"商品库存不足"的**误导性 400** 而非参数错误，排障时易被误判为库存问题。
- **修复建议（P0，四层缺一不可）**:
  1. `CreateOrderRequest.OrderItemLine.quantity` 加 `@NotNull @Min(1) @Max(999)`，Controller 加 `@Valid`；
  2. 相关 `@RequestParam` 入口（如购物车改数量）加 `@Min(1)`；
  3. `OrderServiceImpl.buildLineFromSku` / `createOneOrder` 服务端循环前强制 `quantity == null || quantity < 1` 抛参数异常（防御纵深，不依赖注解）；
  4. `CartServiceImpl.add/updateQuantity` 同步加 `quantity < 1` 拒绝；下单时校验 `payAmount > 0` 兜底。

### 🟠 严重（High）

#### [F-002] 售后退款无累计上限：同一订单明细可重复申请、累计超退
- **Category**: A04 / 退款业务逻辑
- **Confidence**: 9/10
- **位置**: `service/impl/AfterSaleServiceImpl.java:66-93`
- **威胁描述**: 防重复仅排除状态 `0/1/3`（进行中）的售后单，已**完成（4）**的不计入。退款金额上限只对比"该明细实付总额"，**不扣除已退金额**。攻击链：申请退 ¥600（明细总额 ¥1000）→ 商家同意（完成）→ 订单回到"已完成"→ 再次对同一明细申请退 ¥1000 → 累计退款 ¥1600 > 实付 ¥1000。当前模拟支付下 `refundPayment` 第二次不会重复置位，但售后单记录了超额退款承诺；接入真实支付通道即成资金损失。
- **修复建议（已与代码评审 B3 合并为完整方案，缺一不可）**: ① running 防重集合加入终态 4；② 每明细仅一条终态退款单（唯一约束）；③ **累计退款上限：SUM(该 order_item 已退金额) + 本次 ≤ item.totalAmount**（仅做①②挡不住"多次部分退款累计超付"）；④ 换货（type=2）跳过 refundPayment；⑤ 前端字典删除状态 1。

#### [F-003] 短信验证码无试错次数限制，可爆破重置任意账号密码
- **Category**: A07 认证失败
- **Confidence**: 8/10
- **位置**: `service/impl/AuthServiceImpl.java:222-236`（`verifyCode` 无失败计数）；`AuthController.java:60-65`（`/api/auth/forgot` 无频率限制）
- **威胁描述**: 验证码 6 位数字（100 万空间）、TTL 5 分钟、校验错误**不锁定、不计数、不销毁**。攻击者对已绑定手机号的账号调用 `/sms-code?type=forgot`（接口还会回显手机号是否已绑定，便于筛选目标）→ 5 分钟内自动化枚举 → 命中即重置密码接管账号。60 秒重发限制只约束"发送"，不约束"试错"。
- **修复建议（P0）**: Redis 记录 `sms:fail:{type}:{phone}` 计数，错 5 次即作废验证码并锁定 10 分钟；`/forgot`、`/sms-code` 加 IP + 手机号双维度限流；接入图形验证码。

#### [F-004] 支付结果查询接口越权（IDOR）
- **Category**: A01 访问控制
- **Confidence**: 9/10
- **位置**: `service/impl/PaymentServiceImpl.java:77-90`（`query(orderId)` 无归属校验）
- **威胁描述**: 任意登录用户可遍历 `orderId` 查询他人订单的支付流水号、支付状态、支付时间。对比同文件 `pay()` 有 `order.getUserId().equals(uid())` 校验，属明显遗漏。
- **修复建议（P1）**: `query()` 增加与 `pay()` 一致的归属校验。

#### [F-005] 改密/找回密码口令经 URL 查询参数传输
- **Category**: A02 加密失败 / 敏感数据暴露
- **Confidence**: 9/10
- **位置**: `AuthController.java:54`（`PUT /api/auth/password?oldPassword=...&newPassword=...`）、`:61`（`POST /api/auth/forgot?...&newPassword=...`）
- **威胁描述**: 明文新旧密码进入请求 URL，将被 Tomcat access log、反向代理日志、APM、浏览器历史记录留存。口令一旦落盘即长期可恢复。
- **修复建议（P1）**: 改为 `@RequestBody` JSON 传输；上线前确认 access log 中无历史口令残留。

#### [F-006] 短信验证码明文写入后端日志
- **Category**: A02 / A09
- **Confidence**: 10/10（代码确认；README 已自认仅用于开发）
- **位置**: `service/impl/AuthServiceImpl.java:194` — `log.info("【模拟短信】手机号 {} 的 {} 验证码：{}...")`
- **威胁描述**: 配合 F-003，拿到日志即直接拿到验证码。README 明确"生产环境不得如此"，但代码无 profile 隔离，随时可能被带上线。
- **重要背景（三方对账结论）**: 该日志是本交付物找回密码流程在演示环境唯一可用的取码路径，**不能简单删除**。定级为条件阻塞（C 组）：localhost 演示保留，对外部署前必须关闭。
- **修复建议**: 开关化而非删除——`@Value("${app.sms.echo-code:false}")` 配置项，local/demo profile 下开启，生产默认关闭；启动时检测 `非 local profile + echo-code=true` 直接 fail-fast。这样既保住演示，又不留生产隐患。

#### [F-007] 硬编码密钥/口令进入版本库
- **Category**: A02 / A05
- **Confidence**: 9/10
- **位置**: `resources/application.yml:14`（MySQL `root/123456`）、`:36`（JWT secret 明文默认值）、`:12`（`useSSL=false`）
- **威胁描述**: JWT 签名密钥与数据库口令随 Git 提交分发。注：JWT+Redis 双校验使伪造 Token 无法单独生效（缓解因素），但密钥泄露仍扩大攻击面（离线伪造、Redis 被攻破后无第二道防线）；DB 弱口令若 MySQL 对公网/内网暴露即沦陷。
- **已验证的缓解项**: `application-local.yml`（含真实 LLM Key）确认在 `.gitignore` 且 `git log` 全历史从未提交 ✓。
- **修复建议（P1）**: `application.yml` 中密钥改为 `${JWT_SECRET:}` / `${DB_PASSWORD:}` 环境变量注入，无默认值时启动失败；MySQL 启用独立账号 + 强口令 + 禁远程 root。

### 🟡 一般（Medium）

#### [F-008] CORS 通配 origin + allowCredentials
- **位置**: `config/WebConfig.java:29-34` — `allowedOriginPatterns("*")` + `allowCredentials(true)`
- **描述**: 任意站点可携带凭证跨域调用 API。当前鉴权走 Authorization 头（非 Cookie），风险中等；若未来引入 Cookie 即升级为高危。
- **建议（P2）**: 生产环境收敛为前端域名白名单。

#### [F-009] MyBatis SQL 全量打印到 stdout
- **位置**: `application.yml:28` — `log-impl: StdOutImpl`
- **描述**: 生产环境所有 SQL 及绑定参数（手机号、地址等 PII）进入标准输出日志。
- **建议（P2）**: 生产 profile 改为 `slf4j` 且级别 ≥ WARN。

#### [F-010] 关键接口全局无速率限制
- **位置**: `/api/auth/login`（密码爆破）、`/api/chat/send`（LLM 按 token 计费，刷接口=刷账单，且无消息长度上限）、`/api/order`（库存/订单洪泛）
- **建议（P2）**: 登录 5 次/分钟/IP；chat 限频 + content 长度上限（如 2000 字）；下单限频。

#### [F-011] 账号枚举：找回密码回显手机号绑定状态
- **位置**: `AuthServiceImpl.java:174-179`（"该手机号未绑定账号"）
- **建议（P2）**: 统一话术"验证码已发送（若手机号已注册）"。

#### [F-011b] 商家入驻身份证号明文入库，无脱敏无加密
- **Category**: A02 加密失败 / 数据保护
- **Confidence**: 9/10（代码评审员交叉确认）
- **位置**: `entity/MerchantApply.java` idCard 字段；`MerchantServiceImpl.java:79` 直接 `apply.setIdCard(request.getIdCard())` 明文落库；建表 SQL `merchant_apply.id_card` 无加密/脱敏设计
- **威胁描述**: 身份证号属敏感个人信息（PII 高危类目），明文存储后：DB 泄露即全量泄露；管理端审核列表、SQL stdout 日志（F-009）、数据库备份均成为泄露面。
- **修复建议（P2）**: 入库前 AES 加密（密钥走环境变量）或至少展示层脱敏（`110***********1234`）；审核通过后按最小必要原则评估是否需长期留存。

#### [F-011c] 真实 LLM API Key 存在于交付目录，建议按已泄露处理并轮换
- **Category**: A02 / 密钥管理
- **Confidence**: 8/10（与代码评审员交叉确认：`.gitignore` 正确、`git log --all` 全历史零提交，未进版本库 ✓）
- **位置**: `resources/application-local.yml:9`（阿里云 MaaS key，本报告不引用其值）
- **威胁描述**: 文件本身不含在 Git 内，但**会随整个工作区被打包/上传网盘/交付评审**而扩散，实际暴露面等同于半公开。该 key 关联计费账户，被滥用即产生账单损失。
- **修复建议（P1）**: 交付前轮换该 Key；将真实 Key 迁出项目目录（环境变量或外部秘管）；打包脚本显式排除 `application-local.yml`。

#### [F-012] 商家侧存储型 Prompt 注入面
- **位置**: `ChatServiceImpl.java:239-253`（商品名/价格/销量直接拼入 system+user prompt）；商品字段来自商家可控的 `ProductPublishRequest`
- **描述**: 恶意商家可在商品名/tags 中植入"忽略之前指令……"类内容，影响所有咨询该商品的用户的导购回答（虚假宣传、导流话术）。影响面为内容完整性，不涉及数据外泄（上下文无私密数据）。
- **建议（P2）**: 商品文本入库前过滤常见注入关键词；prompt 中将商品数据包裹在明确的结构化标记内；对导购输出做关键词后过滤。

## STRIDE 威胁建模

### 链路一：用户下单支付
`浏览商品 → 加购/直接购买 → 创建订单(预扣库存) → 模拟支付 → 待发货`

| STRIDE | 威胁场景 | 现有缓解 | 残余风险 |
|---|---|---|---|
| 假冒 Spoofing | 盗用他人 Token 下单 | JWT 签名 + Redis 双校验 + 单端互踢 | 低（JWT 密钥硬编码为放大项 F-007） |
| 篡改 Tampering | 篡改下单金额/数量 | 金额取 DB 价格 ✓ | **高：数量可负/零 → 负金额、零元购（F-001）** |
| 抵赖 Repudiation | 用户否认下单/支付 | payment 流水 + order 快照 | 中：无用户侧操作日志（仅管理端有 operation_log） |
| 信息泄露 InfoDisclosure | 查看他人订单/支付 | 订单详情/取消/确认/物流均有归属校验 ✓ | 支付结果查询无校验（F-004） |
| 拒绝服务 DoS | 批量下单占库存不付款 | 取消回补库存 ✓ | 中：无下单限频、无待付款自动超时关单 |
| 提权 EoP | 普通用户调用商家/管理接口 | `@RequireRole` + 拦截器实时查库角色 ✓ | 低 |

### 链路二：售后退款
`申请售后(选明细/金额) → 商家处理 → 拒绝可申诉 → 平台介入 → 完成退款`

| STRIDE | 威胁场景 | 现有缓解 | 残余风险 |
|---|---|---|---|
| 假冒 | 冒充他人申请售后 | 订单归属 + 明细归属双重校验 ✓ | 低 |
| 篡改 | 虚报退款金额 | 金额 ≤ 明细实付校验 ✓ | **高：无累计退款上限，可重复申请超退（F-002）** |
| 抵赖 | 商家/平台否认处理动作 | 平台操作写 operation_log ✓ | 中：商家处理动作未写 operation_log |
| 信息泄露 | 查看他人售后单 | `assertVisible` 三方可见性校验 ✓ | 低 |
| 拒绝服务 | 对同一明细狂刷售后申请 | 进行中唯一约束 ✓ | 低 |
| 提权 | 商家处理他店售后 / 用户调管理接口 | 店铺归属校验 + 角色注解 ✓ | 低 |
